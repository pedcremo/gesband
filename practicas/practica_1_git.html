Pràctica 1 · Treball en equip amb Git i GitHub sobre Gesband

Afegireu una funcionalitat xicoteta a una aplicació real. L'objectiu no és el codi, sinó aprendre a treballar diverses persones sobre el mateix repositori: branques, pull requests, revisió i, sobretot, resolució de conflictes.

  • Durada: 2 hores
  • 6 grups de 3 persones
  • Eines: Git, GitHub, Python 3.13, Django

1. Què és Gesband

Gesband és una aplicació per a gestionar bandes de música: censa de músics, assajos i actuacions, convocatòries, respostes, assistència i avisos. Té dues parts:

  • Servidor (carpeta backend/): Django i Django REST Framework. Inclou el panell de la junta (/panel/) i l'API (/api/v1/).
  • App mòbil (carpeta mobile/): Flutter. En aquesta pràctica no la tocareu.

Treballareu sobre una còpia del projecte preparada per a la classe: github.com/pedcremo/gesband_practicas. El propietari és el professor; per a poder publicar-hi branques necessiteu permís d'escriptura (fase 0).

2. Objectius d'aprenentatge

  • Clonar un repositori, crear branques i fer commits amb missatges clars.
  • Publicar branques a GitHub i obrir pull requests (PR).
  • Revisar el codi d'una altra persona i aprovar o demanar canvis.
  • Entendre per què apareix un conflicte i resoldre'l sense perdre la feina de ningú.
  • Comprovar amb proves automàtiques que, després d'una fusió, tot continua funcionant.

3. Normes del repositori

  • Ningú no fa commits directament a main. Tot entra per PR.
  • Prohibit git push --force en branques compartides.
  • No pugeu .venv/, backend/db.sqlite3, contrasenyes ni dades reals. Useu només dades inventades.
  • Davant d'un conflicte, no esborreu el canvi de l'altra persona per a acabar abans: combineu les dues versions.
  • Un commit = un canvi amb sentit. Missatge en valencià i en present: Afig el compte enrere a la pròxima activitat.

4. Organització del grup

Cada grup té una funcionalitat (apartat 6). Repartiu-vos aquests tres rols:

RolQuè faBranca
A · CodiImplementa la vista, la plantilla o l'endpoint.gN/a-codi
B · ProvesEscriu les proves automàtiques en backend/tests/test_practica_gN.py. Pot començar abans que el codi estiga fet: primer fallaran i, després de la fusió, han de passar.gN/b-proves
C · Documentació i integracióExplica la funcionalitat en el manual de la junta (docs/manuales/junta.md), afig la línia del grup a practicas/CHANGELOG.md i porta la PR final cap a main.gN/c-docs

N és el número del grup. Les tres branques ixen de la branca del grup, gN/funcionalitat, i tornen a ella per PR. Al final, gN/funcionalitat entra en main amb una altra PR.

main

      ├── g3/a-codi    ── PR ──┐               │
      ├── g3/b-proves  ── PR ──┼──► g3/funcionalitat ──► main
      └── g3/c-docs    ── PR ──┘

Fase 0 · Compte de GitHub i accés al repositori (abans de classe)

Sense aquest pas no podreu publicar cap branca. Feu-lo abans de la sessió: l'invitació no arriba al moment.

  1. Si encara no en teniu, creeu un compte en github.com/signup. Useu un nom d'usuari reconeixible (per exemple, nomcognom) i verifiqueu el correu.
  2. Activeu la verificació en dos passos (Settings → Password and authentication). GitHub l'exigeix per a contribuir.
  3. Demaneu accés d'escriptura al propietari: envieu al professor, per Aules FP, el vostre nom d'usuari de GitHub i el vostre grup. No envieu mai la contrasenya.
  4. El professor vos afegirà com a col·laboradors. Rebreu un correu de GitHub: accepteu la invitació des del correu o en github.com/pedcremo/gesband_practicas/invitations. Caduca als 7 dies.
  5. Comproveu-ho després d'iniciar sessió (vegeu el quadre): gh repo view pedcremo/gesband_practicas --json viewerPermission ha de respondre WRITE. Si respon READ, encara no heu acceptat la invitació.

Per a fer git push per HTTPS, GitHub no accepta la contrasenya del compte. Inicieu sessió una vegada amb gh auth login (GitHub CLI) o creeu un personal access token i useu-lo com a contrasenya.

Fase 1 · Posada en marxa (20 min)

Cada persona, en el seu ordinador:

# Identitat de Git (una sola vegada per ordinador)
git config --global user.name "Nom Cognom"
git config --global user.email "el-vostre-correu-de-github@exemple.com"

# Clonar
git clone https://github.com/pedcremo/gesband_practicas.git
cd gesband_practicas

# Entorn de Python i base de dades local (SQLite)
python3.13 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
.venv/bin/python backend/manage.py compilemessages --ignore=.venv
.venv/bin/python backend/manage.py migrate
.venv/bin/python backend/manage.py createsuperuser
.venv/bin/python backend/manage.py runserver

El correu de user.email ha de ser un correu verificat del vostre compte de GitHub (Settings → Emails), o l'adreça …@users.noreply.github.com que hi apareix si teniu el correu ocult. Si no coincideix, GitHub no vos atribueix els commits i en l'avaluació constarà que no heu fet cap. Comproveu-ho amb git config user.email abans del primer commit.

Obriu http://127.0.0.1:8000/admin/, entreu amb l'usuari que heu creat i afegiu una Asociación inventada (per exemple, nom «Banda de Proves» i identificador proves). Després, en una altra terminal:

.venv/bin/python backend/manage.py seed_role_accounts --association proves

Ja podeu entrar en http://127.0.0.1:8000/panel/ com a junta: usuari prova-board, contrasenya Gesband.demo.2026. Creeu dues o tres fitxes de músic i una activitat per a tindre dades.

Si compilemessages falla, instal·leu gettext (sudo apt install gettext). Les proves completes del projecte tarden molt: durant la pràctica executeu només les vostres (apartat 7).

Fase 2 · Escalfament: el primer conflicte (20 min)

Provocarem a propòsit un conflicte dins del grup per a aprendre a resoldre'l amb calma.

  1. Persona C crea la branca del grup i la publica: 
    git switch main
git pull
git switch -c gN/funcionalitat
git push -u origin gN/funcionalitat
  2. Les tres persones la baixen i creen la seua branca: 
    git fetch
git switch gN/funcionalitat
git switch -c gN/a-codi      # o gN/b-proves, o gN/c-docs
  3. Cada persona edita practicas/equips/grupN.md: completa la seua fila de la taula i escriu un lema del grup diferent en la mateixa línia del final. Després: 
    git add practicas/equips/grupN.md
git commit -m "Afig les meues dades a la fitxa del grup"
git push -u origin gN/a-codi
  4. Cada persona obri una PR de la seua branca cap a gN/funcionalitat (no cap a main!). Una altra persona del grup la revisa i la fusiona. La primera entra sense problemes; les altres dues mostraran This branch has conflicts.
  5. Qui té el conflicte el resol en el seu ordinador: 
    git fetch
git merge origin/gN/funcionalitat
# Git avisa: CONFLICT (content): Merge conflict in practicas/equips/grupN.md
    Obriu el fitxer. Veureu marques com aquestes: 
    <<<<<<< HEAD
Lema del grup: Qui no s'equivoca, no fa commits
=======
Lema del grup: Merge o morir
>>>>>>> origin/g3/funcionalitat
    Entre <<<<<<< i ======= hi ha la vostra versió; entre ======= i >>>>>>>, la que ja hi havia en la branca del grup. Decidiu en grup el lema final, esborreu les marques, comproveu que les files de la taula són les tres i acabeu: 
    git add practicas/equips/grupN.md
git commit            # Git proposa un missatge de fusió; deixeu-lo
git push
    La PR s'actualitza sola i ja es pot fusionar.

Idea clau: les files de la taula, cadascuna en una línia diferent, normalment es fusionen soles. El conflicte apareix quan dues persones canvien la mateixa línia o línies del costat.

Fase 3 · Desenvolupament (45 min)

Torneu a posar al dia la vostra branca abans de començar (git fetch i git merge origin/gN/funcionalitat) i treballeu en la funcionalitat de l'apartat 6, cadascú en el seu rol:

  • Feu commits xicotets i freqüents. Publiqueu-los amb git push.
  • Quan acabeu una part, obriu la PR cap a gN/funcionalitat. Descriviu què fa i com es prova.
  • Cada PR la revisa una altra persona del grup, que ha de deixar almenys un comentari en una línia concreta abans d'aprovar-la.
  • Ordre recomanat de fusió: A (codi) → B (proves) → C (documentació). Després de fusionar A i B, les proves de B han de passar en gN/funcionalitat.
  • Totes les cadenes que veu l'usuari, amb {% translate "…" %} en les plantilles o gettext en Python. No editeu els fitxers .po: generarien conflictes enormes i no és l'objectiu.

Fase 4 · Integració en main (25 min)

Ara toca el conflicte de veritat. Els sis grups entraran en main un darrere l'altre, i diverses funcionalitats toquen els mateixos fitxers. A més, tots els grups han d'afegir la seua línia en la primera posició de la llista de practicas/CHANGELOG.md. Qui fusione més tard trobarà més conflictes.

  1. Persona C porta main a la branca del grup: 
    git switch gN/funcionalitat
git pull
git fetch
git merge origin/main
  2. Si hi ha conflictes, git status mostra els fitxers afectats (both modified). Resoleu-los amb tot el grup davant:
    • En CHANGELOG.md, les dues línies han de quedar. L'ordre entre elles no importa.
    • En codi Python o en plantilles, les dues funcionalitats han de continuar funcionant. Si dubteu, parleu amb el grup que ha escrit l'altre canvi.
    • Si dos grups afigen la mateixa configuració, deixeu-la una sola vegada.
  3. Abans del commit de fusió, comproveu que no queda cap marca i que les proves passen: 
    git grep -n -E "^(<<<<<<<|=======|>>>>>>>)"   # no ha d'eixir res
.venv/bin/python backend/manage.py check
.venv/bin/python backend/manage.py test backend.tests.test_practica_gN
git add .
git commit
git push
  4. Obriu la PR gN/funcionalitat → main. La revisa una persona del grup següent (el grup 6 revisa el grup 1). Els comentaris es resolen abans de fusionar.
  5. Si mentre esperàveu la revisió ha entrat un altre grup en main, torneu al pas 1. Quan la PR estiga aprovada i en verd, fusioneu-la.

Si una fusió se us complica massa, podeu cancel·lar-la i tornar a l'estat anterior amb git merge --abort. No useu git reset --hard sense preguntar al professorat.

Fase 5 · Tancament (10 min)

Comproveu en GitHub la pestanya Insights → Network per a veure el dibuix de branques i fusions de tota la classe, i feu el lliurament de l'apartat 8.

6. Funcionalitats per grup

Totes són xicotetes. Si acabeu abans, milloreu les proves o ajudeu el grup que reviseu.

Totes han de respectar dues regles del projecte: cada banda només veu les seues dades (una consulta mai no pot barrejar dades de dues associacions) i les dates es guarden en UTC però es mostren en la zona horària de la banda.

Grup 1 · Músics per corda

En el llistat de músics (/panel/members/), damunt de la taula, mostreu quantes fitxes actives hi ha per corda: Fusta 12 · Metall 9 · Percussió 3.

  • Fitxers: backend/config/panel.py (funció members), backend/templates/members/list.html.
  • Pista: mireu en backend/apps/members/models.py com es relacionen Member, MemberInstrument, Instrument i Section. Useu annotate(Count(...)) i compteu cada músic una sola vegada per corda encara que hi toque dos instruments.
  • Proves mínimes: els comptadors són correctes; les fitxes de baixa no compten; els músics d'una altra associació no apareixen.

Grup 2 · Compte enrere

En el cartell de la pròxima activitat de la pàgina d'inici del panell, afegiu «Hui», «Demà» o «Falten N dies».

  • Fitxers: backend/config/panel.py (funció dashboard) o un filtre nou en backend/apps/activities/templatetags/; backend/templates/shared/dashboard.html.
  • Pista: compteu dies de calendari en la zona de la banda (association.timezone), no blocs de 24 hores: una activitat demà a les 9:00 vista hui a les 23:00 és «Demà».
  • Proves mínimes: la funció de càlcul amb dates fixes (hui, demà, d'ací a 5 dies, canvi d'hora d'octubre); la pàgina d'inici mostra el text.

Grup 3 · Versió en el peu del panell

Totes les pàgines del panell mostren un peu discret: Gesband · versió 0.1.0.

  • Fitxers: backend/config/settings.py (nova opció GESBAND_VERSION = "0.1.0" i registre del processador de context), backend/config/context_processors.py (nou), backend/templates/shared/base.html.
  • Pista: un context processor és una funció que rep la petició i torna un diccionari que arriba a totes les plantilles.
  • Proves mínimes: el panell mostra la versió; amb @override_settings(GESBAND_VERSION="9.9.9") mostra la nova.

Grup 4 · Endpoint de versió

Una adreça pública GET /version/ que respon en JSON {"name": "Gesband", "version": "0.1.0"}, com ja fa /health/.

  • Fitxers: backend/config/settings.py (opció GESBAND_VERSION = "0.1.0"), backend/config/urls.py, i una vista on considereu adequat.
  • Pista: mireu com està feta la ruta health/ en urls.py. Accepteu només GET. No exposeu cap altra dada de la configuració.
  • Proves mínimes: resposta 200 i JSON correcte sense iniciar sessió; POST torna 405; amb override_settings canvia la versió.

Grup 5 · Contacte amb un clic

En el llistat de músics, una columna nova Contacte amb enllaços tel: i mailto: perquè la junta puga telefonar o escriure des del mòbil.

  • Fitxers: backend/templates/members/list.html, un filtre nou en backend/apps/members/templatetags/.
  • Pista: l'enllaç tel: no admet espais: +34 600 000 001 → tel:+34600000001. Si una fitxa no té telèfon o correu, no mostreu l'enllaç buit. Recordeu canviar el colspan de la fila «no hi ha músics».
  • Proves mínimes: el filtre amb números amb espais, guions i buits; el llistat conté els enllaços correctes.

Grup 6 · Duració de l'activitat

En el detall d'una activitat del panell, si té hora de final, mostreu Duració: 2 h 30 min.

  • Fitxers: un filtre nou en backend/apps/activities/templatetags/, backend/templates/activities/detail.html.
  • Pista: ends_at - starts_at és un timedelta. Formats: 45 min, 2 h, 2 h 30 min. Si no hi ha final, o el final és anterior a l'inici, no mostreu res.
  • Proves mínimes: el filtre amb els tres formats i els dos casos sense duració; la pàgina de detall mostra el text.

Tots els grups també modifiquen docs/manuales/junta.md (una explicació breu de la funcionalitat) i practicas/CHANGELOG.md (una línia en la primera posició de la llista). Fixeu-vos en la taula de fitxers: hi ha grups que coincidiran en el mateix fitxer. No és un error de l'enunciat.

7. Com escriure i executar les proves

El projecte usa les proves de Django. Mireu algun fitxer de backend/tests/ (per exemple, test_panel_activities.py) per a veure com es creen una associació, un usuari amb rol de junta i com s'entra en el panell. Esquelet:

from django.test import TestCase


class VersionEndpointTests(TestCase):
    def test_returns_name_and_version(self):
        response = self.client.get("/version/")

        self.assertEqual(response.status_code, 200)
        self.assertEqual(response.json()["name"], "Gesband")

Executeu només el vostre fitxer i, abans de la PR final, també el mòdul del panell que heu tocat:

.venv/bin/python backend/manage.py test backend.tests.test_practica_gN
.venv/bin/python backend/manage.py test backend.tests.test_panel_activities

Quan obriu una PR, GitHub executa automàticament la integració contínua (pestanya Checks). Una PR en roig no es fusiona.

8. Lliurament a Aules FP

Una entrega per grup (la fa la persona C) amb:

  1. L'enllaç a la PR gN/funcionalitat → main fusionada.
  2. Una captura de la funcionalitat en el navegador.
  3. Una captura d'un conflicte abans de resoldre'l (amb les marques) i del mateix fitxer després.
  4. Responeu breument, en un text de grup:
    • Quins conflictes heu tingut, amb quins grups i com els heu resolt?
    • Quin conflicte s'hauria pogut evitar organitzant-vos d'una altra manera, i com?
    • Per què no s'ha de resoldre un conflicte quedant-se sempre amb «la meua versió»?
